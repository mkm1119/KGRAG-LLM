그림: `fig/step1_mapping_full.png` (패널별 `fig/step1_p1.png` ~ `step1_p6.png`, 원본 `fig/step1_mapping.html`)

## 1. 문헌 근거

### 1.1 표기

- 문헌: Zhou, Z. 외 (2023). BIM and ontology-based knowledge management for dam safety monitoring. *Automation in Construction*, 145, 104649.
- **OntoDSMS**: 이 논문이 구축한 댐 안전 모니터링 시스템(DSMS) 도메인 온톨로지의 이름이다. 기술 이름이 아니다.
- **D2RQ**: 이 논문이 만든 것이 아니라 기존 오픈소스 플랫폼이다. 논문은 MySQL에 저장된 모니터링 데이터를 OntoDSMS에 연결할 때 D2RQ를 사용했다(4장, 그림 3).
- **본 연구가 벤치마킹한 것**: D2RQ의 매핑 원리이다. 도구 자체나 OntoDSMS 방법론 전체를 따른 것이 아니다.

랩미팅 자료 표기:
> Zhou 외(2023)가 OntoDSMS 구축 시 관계형 DB 연결에 사용한 D2RQ의 매핑 원리를 벤치마킹하여, 정형 표를 KG 개체로 변환하였다.

### 1.2 벤치마킹한 원리

논문 4장의 설명과 그림 3(수정된 매핑 파일 일부)에 근거한다. D2RQ의 매핑은 "표는 클래스, 열은 속성(DatatypeProperty), 행은 인스턴스, 셀은 값(리터럴)"이라는 네 가지 대응을 매핑 파일의 선언으로 구현한다. 본 연구는 그중 다음 네 가지 원리를 가져왔다.

**원리 1. 행의 키 값으로 개체 식별자를 만든다.**
그림 3의 ClassMap은 `d2rq:uriPattern "item/@@item.item_ID@@"`로 식별자를 만든다. `@@` 사이에 적힌 열(item 표의 item_ID)의 값을 행마다 끼워 넣는 틀이다. item_ID가 7인 행은 `item/7`이라는 식별자를 갖는다. 식별자가 키 값에서 결정되므로 같은 행은 언제나 같은 식별자를 받는다. 그래서 다른 매핑이나 질의가 이 식별자로 개체를 다시 가리킬 수 있다.

**원리 2. 한 표에서 나온 식별자는 모두 같은 클래스의 인스턴스가 된다.**
같은 ClassMap의 `d2rq:class :Item`은 위 틀로 만든 모든 식별자를 온톨로지의 Item 클래스 인스턴스로 선언한다. 논문은 이를 "Converting a table in a database to a class in an ontology"라고 설명한다. 표 하나가 클래스 하나에 대응하고, 표의 각 행은 그 클래스의 인스턴스 하나가 된다.

**원리 3. 열 하나를 속성 하나에 대응시키고, 셀 값을 속성값으로 옮긴다.**
그림 3의 PropertyBridge는 세 가지를 선언한다. `d2rq:belongsToClassMap map:item`은 값을 어느 개체에 붙일지, `d2rq:property :itemName`은 온톨로지의 어떤 속성인지, `d2rq:column "item.Genre"`는 어느 열의 셀 값을 옮길지이다. 논문은 이를 "Converting a column in a table to a DatatypeProperty in an ontology"라고 설명한다. 고정 문자열과 열 값을 조합해야 할 때는 `d2rq:pattern`을 쓴다. 그림 3에서는 rdfs:label을 `"item #@@item.item_ID@@"`로 만든다.

**원리 4. 열과 속성의 대응은 사람이 온톨로지 용어로 정한다.**
논문에 따르면 매핑 파일은 DB 구조로부터 자동 생성된다. 이때 클래스와 속성 이름은 DB의 표 이름과 열 이름을 그대로 쓴다. 이것을 사람이 온톨로지 용어에 맞게 수정한다. 그림 3에서 Genre 열이 `:itemName` 속성에 대응된 것이 그 결과이다. 즉 "어느 열이 어느 속성인가"는 자동으로 정해지지 않고, 온톨로지 설계에 따라 사람이 정한다.

## 2. 우리 구현

### 2.1 방류 승인 표 → Approval, EvidenceSource (그림 ①~⑥)

**입력.** `approval_records_clean.csv`에서 대상 4개 댐(충주, 소양강, 횡성, 광동)의 80행을 쓴다. 한 행은 승인 한 건이다. 열은 순차번호, 관측소코드, 관측소명, 승인년월일시분, 방류시작시간, 접수방류량, 비고, 그리고 출처 열 6개(기관, 내려받은 주소, 원본 파일명, SHA-256 등)이다. 아래 설명은 504행을 예로 든다.

```
순차번호=504, 관측소코드=1003110, 관측소명=충주, 승인년월일시분=2011-06-27,
방류시작시간=2011-06-27 18:00, 접수방류량=2000, 비고=(실제방류는 20시부터)
```

먼저 열마다 역할을 정했다(그림 ①, 원리 4).
- 순차번호는 식별자를 만드는 키이다.
- 관측소명은 라벨에 쓴다.
- 승인년월일시분은 속성이 된다.
- 방류시작시간, 접수방류량, 비고는 내용 속성이 된다.
- 관측소코드는 속성이 아니라 댐과의 관계에 쓴다.
- 출처 열은 근거 개체와 출처 기록에 쓴다.

**과정 1. 식별자 생성 (원리 1, 그림 ②).**
틀 `"APR:" + {순차번호}`에 504를 넣어 승인 개체 `APR:504`를 만든다. 같은 행에서 틀 `"EVI:AP:" + {순차번호}`로 근거 개체 `EVI:AP:504`도 만든다. 키로 순차번호를 고른 이유는 세 가지이다.
- 원본 자료가 승인 한 건마다 매긴 번호이다.
- 전처리에서 중복 행을 지운 뒤에는 표 안에서 유일하다. 그래서 80행은 서로 다른 ID 80개가 된다.
- 원본 자료를 다시 내려받아도 바뀌지 않는다.

ID가 값에서 결정되므로 KG를 다시 만들어도 같은 ID가 나온다. 3단계(관계 연결)는 이 ID로 개체를 찾는다.

**과정 2. 클래스 지정과 라벨 (원리 2, 원리 3의 pattern, 그림 ③).**
- 승인 표에서 나온 `APR:` ID 80개는 모두 Approval 클래스의 인스턴스로, `EVI:AP:` ID 80개는 모두 EvidenceSource 클래스의 인스턴스로 기록한다.
- 라벨은 틀 `"승인 {순차번호} ({댐명})"`으로 만든다. 승인 자료의 관측소명은 "충주"이고 K-water 자료는 "충주댐"이다. 그래서 관측소명을 표준 댐명 사전으로 "충주댐"으로 바꾼 뒤 틀에 넣는다.

결과물(`kgv4_entities.csv`):
```
APR:504,    Approval,       승인 504 (충주댐)
EVI:AP:504, EvidenceSource, 한강홍수통제소 댐방류승인 순차번호 504
```

**과정 3. 열 → 속성 (원리 3, 그림 ④).**
- 승인년월일시분 열은 `approvalTime` 속성에 대응한다. 셀 값의 앞 10글자를 날짜(date)로 읽어 `2011-06-27`을 저장한다(column 대응).
- 방류시작시간, 접수방류량, 비고 세 열은 틀 `"방류시작 {}; 접수방류량 {}㎥/s; 비고: {}"`에 넣어 `approvalContent` 문자열 하나로 저장한다(pattern 대응). 비고가 비어 있으면 앞의 두 값만 넣는다. → 4장 남은 문제
- 관측소코드는 속성으로 만들지 않는다. 3단계에서 `concernsDam` 관계의 끝점을 찾는 데 쓴다.

결과물(`kgv4_properties.csv`):
```
APR:504, approvalTime,    2011-06-27, date
APR:504, approvalContent, 방류시작 2011-06-27 18:00; 접수방류량 2000㎥/s; 비고: (실제방류는 20시부터), string
```

**과정 4. 근거 개체의 속성 (그림 ⑤-가).**
같은 행의 출처 정보를 근거 개체의 속성으로 옮긴다. 근거 개체와 승인 개체는 같은 행에서 나왔으므로, 다른 표를 찾지 않고 바로 `APR:504 —supportedBy→ EVI:AP:504`로 잇는다.
```
EVI:AP:504, sourceTitle,   환경부 한강홍수통제소 홍수예보 댐방류승인
EVI:AP:504, sourceType,    승인자료
EVI:AP:504, sourceLocator, 순차번호 504
```

**과정 5. 출처 기록 (그림 ⑤-나).**
개체마다 다섯 가지를 한 줄로 남긴다: 원본 파일, 원본 안의 위치, 적용한 매핑 규칙의 ID, 값의 성격(origin), 메모.
```
APR:504, approval_records_clean.csv, row_number_in_file=504, MR-APR, real, 승인일은 날짜만 있음
```
- `row_number_in_file`은 원본 CSV(cp949)의 행 번호이므로, 원 파일의 해당 행을 바로 열 수 있다.
- `rule`은 매핑 규칙을 식별한다. D2RQ에서 매핑 파일이 하던 "어떤 규칙으로 만들었는가"의 기록을 대신한다.
- `real`은 원본 값을 가공하지 않고 옮겼다는 뜻이다.

### 2.2 K-water 일자료 → Dam

**입력.** `kwater_mywater_period_daily_long.csv.gz`이다. 한 행은 (댐, 날짜, 변수) 하나의 측정값이다. 댐 기본 정보만 담은 표는 따로 없고, 측정 행마다 댐 코드(DAM_CD), 댐 이름, 댐 유형(DAM_BO_NM_source)이 반복해서 붙어 있다.

**과정.**
- 식별자는 틀 `"DAM:" + {DAM_CD}`로 만든다(원리 1). 충주댐은 `DAM:1003110`이다.
- 같은 DAM_CD를 가진 여러 행은 하나의 Dam 인스턴스로 묶는다.
- 댐 유형 열은 그 댐의 첫 행 값을 `damType` 속성으로 옮긴다(원리 3).
- `damName`에는 표준 댐명을 넣는다.

결과물:
```
DAM:1003110, Dam, 충주댐
DAM:1003110, damName, 충주댐,   string
DAM:1003110, damType, 다목적댐, string
```

### 2.3 K-water 시간자료 → HydrometeorologicalState (HMS)

**입력.** `kwater_mywater_hydr_H_wide.csv.gz`(553,609행)이다.
- 한 행은 (댐 코드, 시각)이다.
- 변수는 열로 펼쳐져 있다: `DATA1_수위(EL.m)`, `DATA2_저수량(MCM)`, `DATA3_강우량(mm)`, `DATA4_유입량(CMS)`, `DATA6_총방류량(CMS)`, `DATA7_저수율(%)`

**과정.**
- 식별자는 틀 `"HMS:" + {DAM_CD} + ":" + {변수명}`으로 만든다. 변수명은 열 머리에서 가져온다. 충주댐 수위는 `HMS:1003110:수위`이다.
- 4개 댐 × 6개 변수로 24개 인스턴스를 만든다.
- 변수명은 `variableType`, 댐 코드는 `stationCode` 속성으로 넣는다.
- 시간별 값 자체는 KG에 넣지 않고 측정 저장소에 둔다. 출처 기록에는 그 값이 있는 열 이름(`DATA1_수위(EL.m)`)을 위치로 남긴다.

결과물:
```
HMS:1003110:수위, HydrometeorologicalState, 충주댐_수위
HMS:1003110:수위, variableType, 수위,    string
HMS:1003110:수위, stationCode,  1003110, string
```

같은 방식으로 댐마다 측정자료 근거 개체 `EVI:KW:{DAM_CD}`(4개)를 만든다.

### 2.4 이 단계의 결과물

- 개체 192개: Approval 80, EvidenceSource 84(승인 80 + 측정자료 4), HMS 24, Dam 4
- 속성 468개: 승인 160, 근거 252, HMS 48, 댐 8
- 개체마다 출처 기록 1줄

이 단계가 끝나면 개체와 속성은 갖춰지지만, 서로 다른 표에서 나온 개체(승인과 댐 등)는 아직 연결되지 않은 상태이다. 연결은 3단계에서 다룬다.

## 3. 데이터 구조에 맞춰 응용한 부분

원리는 그대로 두고, 우리 자료의 구조가 OntoDSMS의 DB와 달라서 구현 방식을 바꾼 부분이다.

**(1) 원본이 DB가 아니라 파일이다 → 값을 옮기고 출처를 기록한다.**
- OntoDSMS의 원본은 MySQL DB였다. D2RQ는 매핑 파일에 DB 연결을 선언하고, 원본 DB를 그대로 둔 채 질의할 때마다 매핑을 거쳐 읽는다.
- 우리 원본은 공공데이터 포털과 K-water에서 내려받은 CSV, JSON 파일이다. 질의를 받을 수 있는 DB가 아니다. 그래서 매핑한 값을 그래프 DB(Neo4j)로 옮겨 저장했다.
- 값을 옮기면 KG의 값과 원본 행의 연결이 끊긴다. 이를 보완하려고 과정 4(근거 개체)와 과정 5(출처 기록)를 추가했다.
- 같은 이유로 매핑 규칙은 별도 매핑 파일 대신 변환 코드에 적었다. 대신 각 개체에 규칙 ID를 남겨 어떤 규칙으로 만들었는지 추적할 수 있게 했다.
- 열이 몇 개뿐이어서, 자동 생성 후 수정하는 단계 없이 처음부터 사람이 대응을 정했다(원리 4).

**(2) 승인 시각 열에 날짜만 있다 → 날짜형으로 옮긴다.**
열 이름은 '승인년월일시분'이지만 원본 값은 모두 `2011-06-27`처럼 날짜뿐이다. 없는 시각을 만들어 넣지 않고, 값의 실제 형태대로 date 자료형으로 저장했다. 이 사실은 출처 기록의 메모("승인일은 날짜만 있음")로 남겼다.

**(3) 댐 기본 정보 표가 없다 → 같은 키의 여러 행을 하나의 인스턴스로 묶는다.**
원리 2는 "행 하나 = 인스턴스 하나"이다. 그런데 우리 자료에서 댐 정보는 측정 행마다 반복되어 있을 뿐, 댐 한 개가 한 행인 표가 없다. 그래서 키(DAM_CD)가 같은 행들을 하나의 Dam 인스턴스로 묶었다. 원리 1에 따라 식별자가 키 값에서 결정되므로, 같은 키의 행들은 자연히 같은 식별자로 모인다.

**(4) 측정 표가 넓은 형태이고 행이 55만 개이다 → (댐 코드, 열 머리)로 인스턴스를 만든다.**
- 원리를 그대로 적용하면 시간자료의 각 행(댐, 시각)이 인스턴스가 되어, 553,609개의 노드가 각각 속성 6개를 갖게 된다.
- 그러나 KG에서 필요한 것은 "어느 댐에 어떤 측정 변수가 있는가"라는 구조이고, 시각별 값은 측정 저장소에서 시각으로 조회하면 된다.
- 그래서 행의 키(DAM_CD)와 열 머리(변수명)를 함께 식별자 틀에 넣어 (댐, 변수)마다 인스턴스를 만들었다. "키 값으로 식별자를 만든다"는 원리 1을, 넓은 표에서 키가 들어 있는 두 곳(키 열과 열 머리)에 적용한 것이다.

**(5) 관측소코드는 다른 개체를 가리키는 열이다 → 속성이 아니라 관계로 만든다.**
승인 표의 관측소코드 값은 K-water의 댐 코드와 같다. 이 값을 문자열 속성으로 두지 않고, 3단계에서 Dam 개체를 찾아 `concernsDam` 관계로 잇는 데 썼다. 이렇게 하면 "충주댐의 승인"을 문자열 비교가 아니라 관계를 따라가서 찾을 수 있다.

## 4. 남은 문제

**approvalContent 병합.**
- 방류시작시간, 접수방류량, 비고는 원본에서 이미 서로 다른 열이고, 각각 시각, 숫자, 문장이라는 분명한 형태를 갖는다. 그래서 이들을 합친 것은 데이터 구조 때문에 응용한 것으로 보기 어렵고, 원리 3(열 하나 → 속성 하나)에서 벗어난 것이다.
- 그 결과 방류 시작 시각과 접수방류량이 문자열 안에 묻혀 있다. "2000㎥/s 이상 승인"이나 "승인 후 몇 시간 뒤 방류 시작" 같은 질의를 할 수 없다.
- 원리대로라면 세 속성으로 나눠야 한다: `dischargeStartTime`(datetime), `requestedDischarge`(decimal, ㎥/s), `remark`(string).
- 고치려면 온톨로지에 속성 정의를 추가하고, KG 재생성, 검증, Cypher 내보내기를 다시 해야 한다.
