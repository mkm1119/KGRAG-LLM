- 10/19 녹취에서 교수님이 하신 질문을 주제별로 모으고, 그때 한 답과 **지금 코드·데이터로 확인한 답**을 붙였다.

- "아직 답할 수 없음"은 문헌을 더 읽어야 하거나 아직 정해지지 않은 것이다. 숨기지 않고 그대로 둔다.

## A. 문헌 표기

### A1. "DDKG는 뭐예요? 뭐의 약자예요?" (05:30) / "논문이에요, 기술이에요, 프로그램이에요?" (06:09)

- 당시: 답하지 못함.
- 답:
  - **DDKG**: Dam Defects Knowledge Graph(댐 결함 지식그래프). Huang 외(2026, *Advanced Engineering Informatics*) 논문이 **만든 결과물(지식그래프)의 이름**이다. 논문 이름이나 프로그램이 아니다.
  - 이 논문은 DDO(댐 결함 온톨로지)를 만들고, OHCF(온톨로지 기반 위험 분류 방법)로 보고서 문장을 분류해서, 위험 댐 22,076개의 KG(DDKG)를 만들었다.
  - **OntoDSMS**: Zhou 외(2023, *Automation in Construction*) 논문이 **만든 댐 안전 모니터링용 온톨로지의 이름**이다. 표(DB)를 온톨로지로 옮기는 기술은 이 논문이 만든 것이 아니라 **기존 오픈소스 플랫폼 D2RQ**를 사용한 것이다.

### A2. "DDKG 3.2.1, 3.2.2, 3.2.3이 섞여 있다, 그 논문에서 프로그램인지 버전인지" (07:00)

- 답: 3.2.1 등은 **논문의 절 번호**다. 단계 이름처럼 쓰면 안 된다.
  - 3.2.1절 = 비정형 문서 전처리, 3.2.2절 = 규칙 기반 추출, 3.2.3절 = LLM 기반 추출(OHCF), 3.3절 = 저장
- 랩미팅 자료에서는 "DDKG 논문 3.2.1절의 전처리 방법"처럼 풀어 쓴다.

### A3. "OntoDSMS가 뭘 어떻게 해서 어떻게 되는지" (07:00)

- 답(OntoDSMS 4장, 6~7쪽 원문):
  1. D2RQ가 DB 구조를 보고 **매핑 파일**(어느 표·열이 온톨로지의 무엇인지 적은 파일)을 자동 생성한다.
  2. 사람이 이 매핑 파일을 온톨로지 용어에 맞게 고친다.
  3. 원칙: 표 → 클래스, 열 → 속성, 행 → 개체, 칸의 값 → 속성값
  4. 데이터를 복사하지 않고, 온톨로지 질의가 오면 D2RQ가 SQL로 바꿔 원래 DB에서 바로 꺼낸다(가상 그래프).
- 아직: OntoDSMS 논문 전체는 리뷰하지 않았다. 왜 이 방식을 골랐는지까지는 리뷰 후 보완.

## B. 매핑: "어떻게 대응시켰나"

### B1. "대응을 설명해 줄 수 있어요?" (08:04) / "해가 왜 동쪽에서 뜨는지가 중요" (09:26) / "여기서 매핑은 무엇인가" (10:04)

- 당시: "첫 열이 충주댐이면 클래스로, 나머지 열은 데이터 프로퍼티로" 정도로 답함.
- 답: 우리 매핑은 **"원본 표의 한 행을 읽어, 미리 정한 규칙대로 개체 1개, 속성값 몇 개, 관계 몇 개를 만들어 세 개의 표에 한 줄씩 쓰는 것"**이다. 규칙은 `step2g_build_kg_v4.py` 코드 안에 적혀 있다.
- 실제 한 건(충주댐 승인 순차번호 504, `approval_records_clean.csv`):

  | 원본 열 | 값 | 무엇이 되나 |
  |---|---|---|
  | (행 전체) | | 개체 `APR:504`, 클래스 Approval |
  | 승인년월일시분 | 2011-06-27 | 속성 approvalTime = 2011-06-27 |
  | 방류시작시간·접수방류량·비고 | 18:00, 2000, (실제방류는 20시부터) | 속성 approvalContent = "방류시작 2011-06-27 18:00; 접수방류량 2000㎥/s; 비고: (실제방류는 20시부터)" |
  | 관측소코드 | 1003110 | 관계 `APR:504 –concernsDam→ DAM:1003110`(충주댐) |
  | 순차번호 | 504 | 출처 개체 `EVI:AP:504` + 관계 `APR:504 –supportedBy→ EVI:AP:504` |

- OntoDSMS 원칙과 비교: 행 → 개체는 같다. 그런데 **세 열을 한 속성으로 합친 것, 관측소코드를 속성이 아니라 관계로 만든 것은 원칙과 다르다.** 앞의 것은 고쳐야 할 점(방류량을 숫자로 조회할 수 없음), 뒤의 것은 댐 개체와 이어야 해서 한 우리 판단이다.

### B2. "우리 적용은 뭐예요?" (10:24) / "여기서 자료는 뭐고 같은 행은 뭐죠?" (10:41)

- 답: "적용" = 위 B1의 규칙을 4개 댐 승인 기록 80행 전부에 돌린 것이다. "행"은 승인 기록 파일의 한 줄(승인 1건)이다.

### B3. "댐 기본 자료는 뭐고, 클래스와 객체 ID는 뭐고, 열 프로퍼티는 뭐예요?" (12:01) / "기본 정보가 무슨 상관이냐" (12:57)

- 답:
  - **댐 기본 자료**: Dam 개체를 만드는 데 쓴 자료다. 실제로는 K-water 자료의 댐 코드(DAM_CD)와 댐 형식을 쓴다. 승인 행이 어느 댐인지(관측소코드 = 댐 코드) 잇는 기준이 된다.
  - **객체 ID**: 개체마다 붙인 고유 이름이다. 규칙은 `클래스 약자:원본 키`이다. 예: `DAM:1003110`(댐 코드), `APR:504`(승인 순차번호), `OPR:504:1`(504번 승인 비고의 첫 번째 운영행위)
  - **열 → 프로퍼티**: 원본 열이 어떤 속성 이름으로 들어가는지(B1 표).

### B4. "AP랑 APR이 다르잖아요. 같아야 검색이 되는 거 아니에요?" (14:13~16:29)

- 당시: "통일해야 할 것 같다"고 답함.
- 답(코드 확인 결과): **둘은 같은 것의 다른 표기가 아니라, 서로 다른 개체다.**
  - `APR:504` = 승인 그 자체(Approval)
  - `EVI:AP:504` = 그 승인이 기록된 출처(EvidenceSource, "한강홍수통제소 댐방류승인 순차번호 504")
  - 둘은 이름을 비교해서 찾는 게 아니라, 같은 행을 처리할 때 `supportedBy` 관계로 바로 이어 둔다. 그래서 검색은 된다.
- 다만 같은 행에서 나온 개체라는 것이 이름에서 안 드러나 헷갈린다 → 이름 규칙을 정리할 필요는 있다(교수님 말씀대로 "클래스 밑에 클래스 프로퍼티처럼" 일관되게).

## C. 개체·관계를 실제로 어떻게 만드나

### C1. "KG가 아니고 클래스를 만들어?" (21:58) / "클래스 변수 입력" (22:32)

- 답: 이 단계는 **클래스(종류)를 만드는 게 아니라, 이미 정한 클래스의 개체를 만들고 속성값을 채우는 것**이다. 클래스는 온톨로지 설계 때 정해져 있다. 교수님 표현대로 "선언된 클래스에 변수(값)를 입력"하는 단계다.
- 랩미팅 자료의 단계 이름을 "KG 구축"이 아니라 "개체 생성과 속성값 입력"으로 바꾼다.

### C2. "연결해 준다는 게 실제로 어떻게 연결되냐, 시작과 끝과 받는 데가 있어야 할 거 아니야" (23:49~25:10)

- 당시: "엑셀 열에 클래스–관계–클래스로 표현했던 걸로 기억, 확인 필요"라고 답함.
- 답: 관계는 `kgv4_relations.csv`의 **한 행 = (시작 개체 ID, 관계 이름, 끝 개체 ID, 규칙, 근거 종류, 비고)**이다. 예:
  ```
  APR:504, concernsDam, DAM:1003110, MR-APR-DAM, real, 승인 레코드의 관측소코드 = 댐 코드
  ```
- 시작과 끝을 찾는 방법은 관계마다 두 가지 중 하나다.
  1. **값을 비교해서 찾는 것**(3종)
     - 승인 → 댐(concernsDam): 승인 행의 관측소코드 = 댐 코드
     - 운영행위 → 댐(performedOnDam): 같은 승인 행의 관측소코드 = 댐 코드
     - 운영기준 → 댐(appliesToDam): 별표3의 댐 이름 = 댐 이름(별표에 코드가 없어 이름으로)
  2. **같은 행을 처리하면서 바로 잇는 것**(나머지)
     - 승인 → 출처(supportedBy), 승인 → 운영행위(authorizes: 같은 승인 행의 비고에서 나온 행위), 댐 → 수문상태(hasHydrometeorologicalState: 댐 × 변수 6종) 등
- 관계마다 근거의 강도를 `origin`으로 남겼다: real 211개(원본 값 그대로), derived 136개(원본에서 유도), constructed 68개(연구용으로 구성: 승인 → 운영행위), name-match 3개(이름 일치).

### C3. "하나하나가 클래스예요, 열 하나가 클래스예요?" (26:53) / "엔티티는 숫자예요, 글자예요?" (27:49) / "충주댐 엔티티의 프로퍼티는 어떻게 알아요?" (28:09) / "테이블 이름이 있을 것 같은데" (29:03)

- 답: KG는 세 개의 표로 저장된다.
  - `kgv4_entities.csv`: (개체 ID, 클래스, 이름표) — 예: `DAM:1003110, Dam, 충주댐`
  - `kgv4_properties.csv`: (개체 ID, 속성 이름, 값, 자료형) — 예: `DAM:1003110, damType, 다목적댐, string`
  - `kgv4_relations.csv`: 위 C2
- 개체는 ID(글자)이고, 숫자·날짜는 속성값으로 들어간다. 충주댐의 속성은 **같은 개체 ID(`DAM:1003110`)를 가진 속성 표의 행들**이다. 이 ID가 세 표를 잇는 열쇠다.

### C4. "클래스는 다 JSON으로 저장돼요?" (29:25)

- 답: JSON이 아니라 **CSV 표 3개**로 저장하고, 이것을 Neo4j에 넣는 명령문으로 바꾼다(E 참고). DDKG는 JSON을 썼고, 우리는 같은 역할을 CSV로 한다.

## D. Dam 클래스의 속성

### D1. "충주댐 밑에 프로퍼티는 뭐가 들어가요?" "코드만 들어가면 끝이야? 왜?" "제원은 안 넣어도 돼요?" (29:48~31:31)

- 아직: 제원을 넣을지는 현장(11/26)에서 확인할 질문 목록과 CQ 재정의에 따라 정한다.

## E. 저장

### E1. "JSON에 어떤 형태로 들어가 있냐, Cypher가 뭐냐, 프로그램이냐" (47:35)

- 답:
  - **Neo4j**: 개체를 점(노드), 관계를 선으로 저장하는 그래프 데이터베이스(프로그램).
  - **Cypher**: Neo4j에 "이런 점을 만들어라, 이런 선을 그어라, 이런 경로를 찾아라"라고 지시하는 명령 언어(관계형 DB의 SQL과 같은 역할).
  - `step7_export_cypher.py`가 CSV 3개를 읽어 명령문 파일 `kgv4_load.cypher`를 만든다. 실제 명령 두 줄:
    ```
    MERGE (n:Entity:Approval {id: 'APR:504'}) SET n.approvalTime = date('2011-06-27'), ...
    MATCH (a:Entity {id: 'APR:504'}), (b:Entity {id: 'DAM:1003110'}) MERGE (a)-[r:concernsDam]->(b)
    ```
    첫 줄 = "APR:504라는 승인 점을 만들고 속성을 넣어라", 둘째 줄 = "APR:504와 DAM:1003110 두 점을 찾아 concernsDam 선을 그어라". MERGE는 없으면 만들고 있으면 그대로 둔다.
- 근거: DDKG 3.3절(추출 결과를 JSON으로 모아 Python 스크립트로 Cypher 생성, Neo4j에 일괄 적재)과 같은 방식.

## F. 검증

### F1. "온톨로지를 검증하는 거예요, KG를 검증하는 거예요?" (39:43)

- 당시: "만든 KG로 온톨로지를 검증한다"고 답함.
- 답: **두 가지를 했고, 구분해야 한다.**
  1. **KG 검증**: 만든 KG가 온톨로지 설계를 지켰는지 본다 (`step6_validate.py` V1~V5).
  2. **온톨로지 검증**: 온톨로지 설계로 CQ에 답할 경로가 있는지 KG에서 따라가 본다 (CQ별 경로 점검, V9·V10).
     - 예: CQ4(과거 승인)는 원래 설계(관계 8개)로는 댐에서 승인 80건 중 63건에만 닿았다. 변경 승인은 운영행위를 만들지 않아 경로가 끊겼기 때문이다. 그래서 승인 → 댐(concernsDam) 관계를 추가했고, 80건 모두 닿았다.

### F2. "KG가 잘못됐을 수도 있잖아요" (40:15~40:33)

- 답: 맞다. 지금 검사는 **"설계를 지켰는가"만 보고, "원본 값을 맞게 옮겼는가"는 보지 않는다.** 예를 들어 승인 날짜를 다른 행의 날짜로 잘못 넣어도, 형식이 날짜이면 통과한다.
- 아직: KG 값과 원본 행을 대조하는 검사(행 번호로 되짚기)가 필요하다. 출처 표(`kgv4_provenance.csv`)에 원본 행 번호가 있어서 만들 수 있다.

### F3. "제약이 뭐예요?" (41:20) / "어떤 규칙을 두는 게 맞고, 맞는지 틀린지 어떻게 판정할 것이냐" (42:07) / "검사 방법, 결과 이렇게만 있으면 돼요" (42:32)

- 답: 제약 = **온톨로지 설계에서 정한 허용 규칙**이다. 코드(`step6_validate.py`)에 목록으로 옮겨 적고, KG 전체를 돌려 어긋난 개수를 센다.

  | 검사 | 무엇을 보나 | 판정 | 결과 |
  |---|---|---|---|
  | V1 | 모든 관계의 시작·끝 클래스가 허용된 쌍인가 (예: concernsDam은 Approval → Dam만 허용) | 어긋난 관계 0개면 통과 | 통과 (0) |
  | V2 | 클래스마다 정한 필수 속성이 다 있는가 (예: Approval은 approvalTime, approvalContent) | 빠진 것 0개면 통과 | 통과 (0) |
  | V3 | 날짜·시각·수치의 형식이 맞는가 (예: 날짜는 YYYY-MM-DD) | 틀린 것 0개면 통과 | 통과 (0) |
  | V4 | 수문상태·운영행위·승인·기준이 모두 출처에 연결되었나 | 출처 없는 것 0개면 통과 | 통과 (0) |
  | V5 | 승인의 댐과 그 승인이 허가한 운영행위의 댐이 같은가 | 다른 것 0개면 통과 | 통과 (0) |

- 왜 이 규칙인가: V1~V3은 온톨로지 설계의 관계 정의역·치역, 필수 속성, 값의 종류이고(Noy 5~6단계에 해당), V4는 "모든 사실은 출처까지 추적돼야 한다"는 연구 목적, V5는 두 경로로 같은 댐에 닿아야 한다는 일관성이다.
- 정정: 랩미팅 자료에서 이 검사의 근거로 든 "DDKG 식 (10)~(11)"은 맞지 않는다. DDKG의 제약 검사는 **LLM이 낸 분류 결과(위험 형태–부위 쌍)가 말이 되는지**를 보는 것이지, 완성된 KG를 검사하는 것이 아니다. DDKG 저자들도 결론에서 "구축된 KG 자체는 체계적으로 평가하지 않았다"고 썼다.
- 아직: Noy 원문 대조는 하지 않았다. "규칙이 맞는지 어떻게 판정하나"(규칙 자체의 타당성)는 지금 방법으로는 답이 없다 → 검증 데이터셋(질문–정답) 과제로 이어진다.

## G. 검색·답변

### G1. "CQ1~6 중 뭔지를 LLM으로 판단한다는 거죠" (50:08)

- 답: 맞다. LLM이 질문에서 `{"intent": ["CQ1", "CQ5"], "dam": "충주댐", "period": "전체"}`를 뽑고, 그다음은 코드(`step9_retrieve.py`)가 처리한다.
  - 입력 확인: 의도가 CQ1~CQ6 밖이거나, 댐이 4개 밖(예: 팔당댐)이거나, 날짜 형식이 틀리면 **조회하지 않고 거부**한다.

### G2. "의도별 경로가 완벽하냐, 어디까지 끌고 올 것인가, 끝없이 끌고 갈 수 있잖아요" (50:37~51:17)

- 답: 경로는 의도마다 **미리 고정**되어 있고(`intents.json`), 길이는 **댐에서 1~2단계**다.
  - CQ1: 댐 → 수문상태(1단계) → 저장소에서 최근 값
  - CQ3: 댐 ← 운영행위(1단계) ← 승인(2단계)
  - CQ4: 댐 ← 승인(1단계)
  - CQ5: 댐 ← 운영기준(1단계) → 출처 → 문서 원문
  - CQ6: 위에서 찾은 것 → 출처(1단계)
- "어디까지"를 정한 기준은 **각 CQ의 답에 필요한 클래스까지**다. 그 밖으로는 가지 않는다.
- 아직(한계로 적어야 할 것): 경로가 완전한지는 검증하지 않았다. CQ 밖의 질문은 답할 수 없다. 의도 추출이 흔들리면(같은 질문 5번 중 4번 CQ2 누락) 필요한 경로를 아예 타지 않는다.

### G3. "미리 정의하는 게 맞는가" (52:16) / "LLM으로 판단하게 하는 방법도" (52:29) / "입력을 뭘로 해주지" (54:42)

- 답: 지금은 답이 정해지지 않은 질문이다. 교수님 제안(소형 LLM이 어디까지 따라갈지 판단)과 Zhang(2025)의 의도 투표 방식을 비교해 정한다.
- 아직: Zhang 논문 리뷰가 필요하다.

### G4. CQ 재정의: "질문 자체가 CQ가 아니라 질문과 정보의 관계가 CQ" (56:29~59:34)

- 답: 검토 과제로 남긴다. 판단("방류해야 하나")은 LLM이 하고, 우리 KG는 그 판단에 필요한 정보("지금" → 현재 수문값, "방류" → 승인·운영행위)를 주는 역할로 CQ를 다시 쓰는 방향이다.
