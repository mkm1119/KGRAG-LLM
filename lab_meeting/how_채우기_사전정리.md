# how 채우기 사전 정리

10/16 랩미팅 자료(10/19 발표본)를 절 순서대로 다시 보면서, 세 가지를 정리했다.

1. **채워야 할 how**: 지금 자료에 "~했다"로만 적혀 있고, 실제로 무엇을 입력받아 어떤 규칙으로 처리해 무엇이 나오는지가 빠진 곳
2. **개선할 점**: 10/19 교수님 피드백과, 코드를 다시 확인하면서 발견한 문제
3. **DDKG로 설명되지 않는 부분**: 자료에서 DDKG를 근거로 들었지만 원문을 다시 읽어 보니 DDKG가 그 일을 하지 않거나, 처음부터 DDKG 범위 밖이어서 다른 근거가 필요한 곳

확인 기준
- DDKG: Huang 외(2026), *Advanced Engineering Informatics* 76, 104987. 레포의 `references/evidence_literature/46_DDKG.pdf` 원문을 다시 읽고 확인함.
- 우리 코드: `step2g_build_kg_v4.py`(구축), `step6_validate.py`(검증), `step7_export_cypher.py`(저장)는 직접 읽고 확인함. 검색·답변 쪽 코드(`step9_retrieve.py`, `step10_bundle.py`, `intents.json`)와 비고 분류 코드(`step2_operation_from_remarks.py`)는 아직 읽지 않았으므로, 그 부분은 "확인 필요"로 표시함.
- Zhang(2025), OntoDSMS(2023), Noy & McGuinness(2001), Li(2025)는 이번에 다시 읽지 않았다. 해당 문헌에 관한 서술은 "원문 확인 필요"로 표시함.

## 0. 먼저 알아 둘 DDKG의 범위

DDKG를 한 문단으로 정리하면 이렇다. 중국 저수지 운영관리 플랫폼의 **정형 표**(댐 기본 속성, 수문 기록, 위치)와, 22,076개 위험 댐의 **안전평가 보고서 문장**을 가지고 **댐 결함 KG**를 만든 연구다. 논문의 기여는 거의 전부 **보고서 문장에서 결함 형태(HazardForm)와 결함 부위(HazardComponent)를 뽑아 온톨로지의 3단계 하위 클래스로 분류하는 방법(OHCF)**에 있다. OHCF는 LLM 미세조정(LoRA), 온도를 바꿔 여러 번 추론한 결과의 투표, 온톨로지 제약 충돌 검사, 전문가 검토와 온톨로지 확장의 네 단계로 이루어진다.

그래서 DDKG가 **자세히 설명하는 것**과 **하지 않는 것**이 분명히 나뉜다.

DDKG가 자세히 설명하는 것
- 온톨로지를 Noy 7단계로 만들고, 모든 최상위 클래스를 Dam에 연결하는 구조 (3.1, 표 1·2)
- 비정형 문서의 전처리: 마크다운 변환, OCR, 정규식으로 블록 경계 찾기, 하나의 말뭉치로 합치기 (3.2.1, 식 2)
- 고도로 정형화된 문장에서 정규식으로 값 뽑기 (3.2.2, "홍수방어 안전등급은 C등급이다" → C)
- LLM으로 문장을 조각내고 분류하는 방법, 투표, 제약 충돌 집합 A와 판정 함수 V, 전문가 검토 (3.2.3, 식 3~11)
- 추출 결과를 JSON으로 모아 Python 스크립트로 Cypher를 만들어 Neo4j에 적재 (3.3, 4.3.1)
- 조건을 걸어 Cypher로 결함 분포를 조회하는 예시 (4.3.2)

DDKG가 하지 않는 것
- **정형 표를 KG로 옮기는 방법**: 3.2.1에서 "플랫폼의 정형 표가 최상위 클래스 c1~c4의 데이터 요구를 대부분 충족한다"고만 쓰고, 표의 열·행을 어떻게 노드와 속성으로 옮겼는지는 설명하지 않는다.
- **개체 사이의 관계를 실제로 어떻게 찾아 잇는지**: 관계의 종류(object property)는 정의하지만, 어떤 키가 일치할 때 두 노드를 잇는지는 쓰지 않는다.
- **완성된 KG 전체를 검증하는 방법**: 3.2.3의 제약 검사는 LLM이 낸 분류 라벨 쌍을 검사하는 것이지, 만든 KG의 관계·속성을 검사하는 것이 아니다. 4.2의 평가도 분류 정확도(P, R, F1)다.
- **CQ(Competency Question)**: 원문에 나오지 않는다.
- **질의응답, LLM 답변 생성, RAG, 의도 파악, 근거 묶음**: 원문에 없다. 4.3.2의 조회는 사람이 쓴 Cypher로 분포를 보는 분석용 조회다.
- **시계열 측정값을 KG 밖에 두고 키로 찾아가는 구조**: 원문에 없다. DDKG는 수문 지표도 Parameter 노드로 KG 안에 넣었다(표 7, Parameter 76,152개).

이 범위를 기준으로 아래 각 절을 보면, **KG 구축의 일부(전처리, 문서 추출, 저장)는 DDKG로 설명되지만 정형 매핑, 관계 연결, KG 검증, 3장 전체는 DDKG로 설명되지 않는다.**

## 1. 공통적으로 빠진 how의 형태

절마다 반복되는 문제는 같은 모양이다. 자료에는 「필요한 이유 → 문헌에서 가져온 원리 → 우리 적용(그림)」이 있는데,

- **문헌의 원리**가 한두 문장 요약이다. 그 문헌이 무엇을 입력으로 받아, 어떤 절차와 수식으로, 무엇을 출력했는지가 없다. 그래서 교수님이 "OntoDSMS가 뭘 어떻게 하는지 없다", "해가 동쪽에서 뜬다만 있다"고 하셨다.
- **우리 적용**이 그림 한 장이다. 그림에는 결과 예시가 있지만, 어떤 규칙(코드의 어느 부분)이 어떤 입력을 어떻게 바꾸었는지가 문장으로 없다.
- **문헌과 우리의 차이**가 적혀 있지 않다. 그래서 "따라 했다"로 읽히는데, 실제로는 다르게 한 곳이 여러 군데 있다(아래 각 절 참고). 다르게 한 곳을 숨기지 않고 "여기는 문헌과 다르게 했고 이유는 이것"이라고 써야 주관적 판단이라는 지적을 피할 수 있다.

따라서 how를 채울 때 절마다 다음 네 가지를 문장으로 쓴다.
1. 문헌은 어떤 문제를 풀려고, 무엇을 입력으로, 어떤 절차로, 무엇을 만들었는가 (원문 절·식·그림 번호와 함께)
2. 우리는 같은 단계에서 무엇을 입력으로, 어떤 규칙으로, 무엇을 만들었는가 (실제 데이터 한 건을 처음부터 끝까지 따라가며)
3. 문헌과 같은 점, 다른 점, 다르게 한 이유
4. 그래서 남은 문제

## 2. 절별 정리

### 1장. Ontology 구조와 개념 (1.1 용어, 1.2 CQ, 1.3 Class·Relation·Data Property)

**채워야 할 how**
- CQ 6개를 어떤 절차로 정했는지. 지금은 결과(CQ1~CQ6)만 있다. 연구 목적에서 어떻게 전체 질문이 나왔고, 전체 질문을 어떤 기준으로 6개로 나눴는지.
- CQ에서 Class 6개, Relation 9개, Data Property가 어떻게 나왔는지. 예를 들어 CQ3("실제로 수행된 운영행위")가 왜 Operation이라는 Class와 operationType, operationTime이라는 속성이 되는지, CQ마다 어떤 Class와 관계가 필요한지를 대응시켜야 한다.
- 관계 1개(concernsDam)를 추가한 과정. 어떤 CQ에 답하려고 했을 때 무엇이 막혀서 추가했는지(CQ4, 도달 가능한 승인 63건 → 80건).

**개선할 점**
- Dam의 속성이 damName, damType 두 개뿐이다. 교수님이 "댐 제원(높이, 폭)은 안 넣어도 되냐"고 물으셨다. 참고로 DDKG는 댐 높이, 저수용량, 특성 수위 같은 지표를 Parameter라는 최상위 클래스로 두었다(3.1, 4.3.1). 우리 CQ 범위에서는 빠져도 되지만, "왜 안 넣었는지"를 CQ 범위로 설명할 수 있어야 한다.
- 10/19 회의에서 교수님이 CQ를 "질문 문장"이 아니라 "질문 속 단어·정보와 필요한 정보 사이의 관계"로 다시 정의하자고 제안하셨다. 이 절은 그 결정에 따라 크게 바뀔 수 있으므로, how 정리는 현재 정의 기준으로 하되 재정의 검토 항목으로 따로 남긴다.

**DDKG로 설명되는가**
- **일부만.** Noy 7단계를 쓴 점, 모든 최상위 클래스를 Dam에 연결하는 구조는 DDKG 3.1(표 1·2)로 설명된다.
- **CQ로 범위를 정하는 방법은 DDKG에 없다.** DDKG에는 CQ가 나오지 않는다. 근거는 Noy & McGuinness(2001)의 1단계(범위 결정과 CQ)와 Li(2025)로 가져와야 한다. *(원문 확인 필요)*

### 2.1 사용 데이터

**채워야 할 how**
- 자료마다 원본 형태(파일 형식, 열 구성, 행 단위가 무엇인지), 기간, 대상 댐, 건수.
- 왜 이 자료들을 골랐는지를 CQ와 연결해서. 예: CQ4에 답하려면 승인 기록, CQ5에 답하려면 별표3.
- 규정은 왜 홍수기 제한수위(별표3)만 가져왔는지. 녹취에서 "테스트만 해보려고 별표3 부분만"이라고 했는데, 이것을 범위 결정으로 문서에 남겨야 한다.

**개선할 점**
- 교수님이 "수문·기상 시간 정보가 댐별로 들어가냐", "댐 기본 정보가 무슨 상관이냐"고 물으셨다. 자료마다 어떤 Class를 채우는 데 쓰이는지를 함께 적으면 이 질문이 사라진다.

**DDKG로 설명되는가**
- 해당 없음(데이터 소개). 다만 DDKG 4.1처럼 "자료 출처 → 어떤 클래스에 쓰이는지"를 나눠 쓰는 서술 방식은 참고할 만하다.

### 2.2 구축 절차 개요

**채워야 할 how**
- 6단계 각각의 입력과 출력 파일. 지금 그림은 단계 이름만 있다. 예: 단계 2의 입력은 `approval_records_clean.csv`, 출력은 `kgv4_entities.csv`, `kgv4_properties.csv`, `kgv4_relations.csv`, `kgv4_provenance.csv`.

**개선할 점**
- 교수님이 "DDKG 3.2.1, 3.2.2, 3.2.3이 섞여 있다, 논문의 프로그램인지 버전인지 모르겠다"고 하셨다. 문헌의 절 번호를 단계 이름처럼 쓰지 말고, "DDKG 논문 3.2.1절에서 설명한 전처리 방법"처럼 풀어 쓴다.
- "DDKG의 구성(출처와 전처리 → 지식 추출 → 저장)을 따르고"라고 썼는데, 아래에서 보듯 정형 매핑, 관계 연결, 검증은 DDKG의 구성이 아니다. 개요에서 단계마다 어느 문헌에서 왔는지를 정확히 나눠 적어야 한다.

**DDKG로 설명되는가**
- **큰 순서(전처리 → 추출 → 저장)만.** DDKG 그림 1·3의 구성은 온톨로지 구축 → 지식 추출 → 지식 융합(저장)이다. 우리 6단계 중 "구조화 매핑", "관계 연결", "검증"은 DDKG 구성에 별도 단계로 없다.

### 2.3 단계 1. 전처리

**채워야 할 how**
- 자료마다 무엇을 골라내고(대상 댐 4개, 기간), 무엇을 중복으로 판단해 지웠는지(어떤 열이 같으면 중복인지), 표기를 어떻게 통일했는지(시각 형식, 숫자 형식, 결측 표기).
- 전처리 전후 건수와 실제 예시 한 건. 교수님이 "처리되면 어떻게 되는지, 뭐가 남는지, 왜 그렇게 남아야 하는지"를 물으셨다.
- 어느 코드가 하는지. *(코드 확인 필요: `build_normalized.py` 등)*

**개선할 점**
- 교수님 질문 그대로 "전처리 결과로 무엇이 남는지"를 예시로 보여야 한다.

**DDKG로 설명되는가**
- **대부분 설명되지 않는다.** 자료에서는 DDKG 3.2.1을 원리로 들었는데, DDKG 3.2.1의 전처리는 **비정형 문서(PDF, DOC, PNG)만** 대상이다. 형식 변환(마크다운), OCR, 정규식으로 지식이 있는 블록의 경계를 찾아 잡음을 지우고 하나의 말뭉치 T로 합친다(식 2). 정형 표는 전처리 대상으로 언급하지 않는다.
- 우리 전처리의 대부분은 **정형 표**(승인 기록, 수문 자료)의 대상 선택, 중복 제거, 표기 통일이다. 이것은 DDKG 3.2.1이 다루지 않는다. 별표3(규정 문서)에서 별표 단위를 잘라내는 부분만 DDKG 3.2.1의 "블록 경계 찾기"와 원리가 같다.
- **정형 표 전처리는 다른 근거가 필요하거나, 근거 없이 일반적인 데이터 정제로 설명해야 한다.** 이 부분은 "자체 판단(일반적 정제)"으로 정직하게 쓰는 것이 낫다.

### 2.4 단계 2. 구조화 자료 매핑

10/26에 1차 정리를 했다(승인 기록 순차번호 504번 추적). 요점만 다시 적는다.

**채워야 할 how**
- OntoDSMS가 쓴 기술은 논문이 만든 것이 아니라 오픈소스 플랫폼 D2RQ다. D2RQ는 DB 구조에서 매핑 파일을 자동 생성하고, 사람이 온톨로지 용어에 맞게 고치며, 표→Class, 열→DatatypeProperty, 행→Instance, 셀 값→Literal의 네 원칙으로 대응시키고, 값을 복사하지 않고 가상 RDF 그래프로 조회한다(OntoDSMS 4장, 6~7쪽).
- 우리 코드는 매핑 파일 없이 규칙이 `step2g_build_kg_v4.py` 안에 직접 적혀 있다. 승인 한 행에서 Approval 개체(`APR:504`)와 EvidenceSource 개체(`EVI:AP:504`)가 생기고, 승인년월일시분은 approvalTime으로, 관측소코드는 Dam으로 가는 concernsDam 관계로 바뀐다.

**개선할 점**
- 방류시작시간, 접수방류량, 비고 세 열을 approvalContent라는 한 문장으로 합쳤다. 열→속성 1:1 원칙과 다르고, 방류량을 숫자로 조회할 수 없다.
- 매핑 규칙을 한눈에 볼 표(열 → Class.속성, 규칙 ID)가 없다.
- APR와 AP는 별개 개체라 연결에는 문제가 없지만, 같은 행에서 나왔다는 것이 이름에서 드러나지 않는다. 교수님이 표기 통일을 지적하셨다.
- 자료에 그린 OntoDSMS 대응 표에는 "댐 표 → Dam" 예시가 있는데, 우리 Dam 개체는 MyWater 자료의 DAM_CD와 하드코딩한 댐 목록으로 만든다. 예시와 실제가 다르다.

**DDKG로 설명되는가**
- **설명되지 않는다.** 앞에서 본 것처럼 DDKG는 정형 표를 KG로 옮기는 방법을 쓰지 않았다. 이 단계의 근거는 **OntoDSMS(Zhou 2023)**이며, 실제로는 OntoDSMS가 사용한 **D2RQ의 매핑 원칙**이다. 관측소코드를 속성이 아니라 관계로 만든 것은 OntoDSMS 4원칙에 없으므로 별도 설명이 필요하다.

### 2.5 단계 3. 문서 자료 추출 (비고 → 운영행위, 별표3 → 운영기준·문서 저장소)

**채워야 할 how**
- 비고 → 운영행위: 비고 문구를 어떤 키워드나 정규식으로 어떤 operationType(초기방류, 증가방류, 탄력적 방류 등)에 대응시켰는지 규칙 목록 전체, 비고 하나에서 운영행위가 여러 개 나오는 경우의 처리, 시각을 어디서 가져오는지(비고에 적힌 시각이 있으면 그것, 없으면 방류시작시간), 어느 규칙에도 맞지 않는 비고는 어떻게 되는지(건수 포함). *(코드 확인 필요: `step2_operation_from_remarks.py`)*
- 별표3 → Criterion: 연계운영규정 XML에서 별표3을 어떻게 찾고, 문자로 그린 표를 어떻게 행·열로 읽고, 댐 이름을 어떻게 맞추고, 홍수기 제한수위 값을 어떤 패턴으로 뽑는지(코드 137줄의 정규식). 왜 댐 이름으로만 연결되는지(별표에 코드가 없음).

**개선할 점**
- 녹취에서 학생 스스로 "승인 비고에는 승인 이유가 아니라 방류 행위가 적혀 있어서 Operation을 따로 만들었다"고 설명했다. 이 판단(승인과 실제 운영행위를 구분하고, 비고를 운영행위 데이터로 쓴 것)은 문헌에서 온 것이 아니라 자료를 보고 한 설계 판단이다. 판단이라고 밝히고, Operation이 "실행 확인이 아니라 연구용 구성"이라는 점(코드 주석 110줄, 관계 origin=constructed)을 자료에도 써야 한다.

**DDKG로 설명되는가**
- **원리는 설명되지만, 우리 자료가 DDKG의 조건과 다르다.** DDKG 3.2.2는 "결과가 고도로 정형화된 형태로 서술되어" 정규식으로 바로 뽑을 수 있는 경우에만 규칙을 쓴다. 대상도 안전평가 등급(A/B/C) 하나다. 형태가 다양한 결함 서술은 규칙이 아니라 LLM(3.2.3)으로 처리한다.
- 비고는 "탄력적 조정", "점증 방류", "실제방류는 20시부터"처럼 표현이 일정하지 않은 짧은 자유 서술이다. DDKG 기준으로 보면 규칙과 LLM의 경계에 있는 자료다. 그래서 "비고는 정해진 형태라 규칙을 썼다"는 주장은 **비고 문구의 실제 분포(겹치는 문구 비율, 규칙에 안 맞는 건수)를 보여야** 성립한다.
- 비고에서 **시각을 뽑는 것**, 별표3의 **문자로 그린 표를 행·열로 읽는 것**은 DDKG에 없다. 각각 우리 자료에 맞춘 처리로 설명해야 한다.

### 2.6 단계 4. 관계 연결

**채워야 할 how**
- 관계 9개 각각에 대해, 어떤 두 개체를 무엇이 일치할 때 잇는지. 코드에서 확인한 내용은 이렇다.
  - Approval –concernsDam→ Dam: 승인 행의 관측소코드 = 댐 코드(DAM_CD)
  - Approval –supportedBy→ EvidenceSource(승인자료): 같은 행을 처리하면서 바로 연결(순차번호)
  - Approval –authorizes→ Operation: 같은 승인 행의 비고에서 나온 운영행위(순차번호), origin=constructed
  - Operation –performedOnDam→ Dam: 승인 행의 시설 코드
  - Dam –hasHydrometeorologicalState→ HydrometeorologicalState: 댐 코드 × 변수 6종을 모두 조합해 생성
  - Criterion –appliesToDam→ Dam: 별표3의 시설명이 댐 이름과 일치(코드 없음, name-match)
  - 나머지 supportedBy: 같은 반복문에서 출처 개체와 직접 연결
- 결과가 어떤 형태로 저장되는지: `kgv4_relations.csv`의 한 행이 (주어 ID, 관계명, 목적어 ID, 규칙 ID, origin, 비고)이다. 교수님이 "시작과 끝과 받는 데가 있어야 할 것 아니냐", "클래스–관계–클래스가 한 행에 있냐"고 물으신 답이 이것이다.

**개선할 점**
- "자료에 적힌 값이 일치하는 개체 쌍에만"이라고 썼지만, 실제로는 대부분 **같은 행을 처리하는 반복문 안에서 바로 연결**하는 것이고, 값을 비교해 찾는 것은 concernsDam·performedOnDam(코드 일치)과 appliesToDam(이름 일치)뿐이다. 이 구분을 정확히 써야 한다.
- 관계마다 origin(real, derived, constructed, name-match)을 기록해 두었는데 자료에는 나오지 않는다. 근거의 강도가 다르다는 것을 보여 줄 좋은 재료다.

**DDKG로 설명되는가**
- **설명되지 않는다.** 자료에서는 "Noy Step 7, DDKG의 7단계 중 ⑦"을 들었는데, DDKG 3.1의 ⑦은 "인스턴스 생성"이라는 단계 이름만 나열한 것이고, 관계를 어떻게 찾아 잇는지는 설명하지 않는다. DDKG 4.3.1도 "온톨로지의 의미 제약에 따라 각 댐이 속성·평가·결함 노드와 연결된다"고만 쓴다.
- 근거는 Noy & McGuinness의 7단계(인스턴스 생성과 슬롯 값 채우기)와 Li(2025)의 "근거가 있을 때만 관계를 만든다"로 가져와야 한다. *(두 문헌 원문 확인 필요)*

### 2.7 단계 5. 검증

**채워야 할 how**
- 코드(`step6_validate.py`)가 실제로 하는 검사는 아래와 같다. 자료의 "제약 5개"와 대응시켜 각각 무엇을, 어떤 기준으로, 결과가 어땠는지를 써야 한다. 교수님이 "검사 방법, 결과 이렇게만 있으면 된다"고 하셨다.
  - V1 관계 양 끝의 Class 쌍이 허용 목록(PAIRS)에 있는가
  - V2 Class마다 정해 둔 필수 속성(ONTO_PROPS)이 모두 있는가
  - V3 날짜(YYYY-MM-DD), 시각(YYYY-MM-DDTHH:MM), 기준값(숫자) 형식이 맞는가
  - V4 HMS, Operation, Approval, Criterion이 모두 근거(EvidenceSource)에 연결되었는가
  - V5 승인의 댐(concernsDam)과 그 승인이 허가한 운영행위의 댐(performedOnDam)이 같은가
  - V6, V7 온톨로지에 없는 속성·관계가 있는가(정보)
  - V9, V10 CQ4 기준으로 댐에서 도달할 수 있는 승인 수, 관계 추가 전과 후(정보)
- 허용 목록(PAIRS, ONTO_PROPS)이 어디서 왔는지: 1.3절 온톨로지 설계를 코드에 옮겨 적은 것이다.

**개선할 점**
- "KG로 온톨로지를 검증하는 것이냐, KG를 검증하는 것이냐"는 질문에 답이 갈렸다. 코드를 보면 V1~V5는 **KG가 온톨로지 설계를 지켰는지(KG 검증)**이고, V9·V10은 **온톨로지 설계로 CQ에 답할 경로가 있는지(온톨로지 검증)**다. 두 가지를 나눠 써야 한다.
- CQ로 도달 가능성을 확인한 것은 CQ4 하나뿐이다. CQ1~CQ6 전부에 대해 같은 확인을 하지 않았다.
- 교수님 지적: KG는 온톨로지로 만든 것이라, KG 오류(데이터를 잘못 넣음)와 온톨로지 오류(설계 부족)를 구분할 방법이 필요하다. 지금 검사는 데이터 값이 원본과 같은지(매핑이 맞는지)는 보지 않는다.
- 검증 파트가 가장 약하다는 평가가 있었고, 검증 데이터셋 구축이 별도 과제로 나왔다.

**DDKG로 설명되는가**
- **설명되지 않는다. 자료에서 가장 크게 어긋난 곳이다.** 자료에는 "Ontology 제약으로 결과를 판정한다(DDKG 3.2.3 식 (10)~(11))"라고 썼는데, DDKG의 충돌 집합 A는 **LLM이 낸 분류 결과에서 결함 형태(c5)와 결함 부위(c6) 라벨 쌍이 공학적으로 말이 안 되는 조합**을 모아 둔 것이다. 예: "파랑벽 정상 표고 부족"을 (차수 표고 부족, 댐 차수체)로 분류하면 충돌. 판정 함수 V는 그 라벨 쌍이 A에 있으면 False를 낸다. 즉 **추출 단계에서 분류 결과 하나하나를 검사하는 장치**다.
- 우리 V1~V5는 **완성된 KG의 관계와 속성이 설계를 지켰는지** 검사한다. 대상, 시점, 판정 기준이 모두 다르다. "충돌하는 조합을 미리 정해 두고 걸리면 거른다"는 발상만 비슷하다.
- "False로 걸린 것을 전문가가 검토해 온톨로지를 확장한다"도 DDKG에서는 **처음 보는 결함 개념**이 나왔을 때 노드를 추가하는 것이고, 우리처럼 **CQ에 답할 경로가 끊겨서** 관계를 추가하는 것과는 계기가 다르다.
- 우리 검사의 근거로는 Noy & McGuinness의 5~6단계(속성의 도메인·범위, 값의 종류와 제한), CQ로 온톨로지를 점검하는 방법(Noy 1단계)이 더 맞다. *(원문 확인 필요)* KG 품질 검증에 관한 별도 문헌을 찾아야 할 수도 있다.

### 2.8 단계 6. 저장

**채워야 할 how**
- `step7_export_cypher.py`가 하는 일: CSV 세 개(개체, 속성, 관계)를 읽어, 개체마다 `MERGE (n:Entity:Approval {id:'APR:504'}) SET ...` 한 줄을 만들고, 날짜·시각·숫자는 Cypher 타입으로 바꾸며, 관계마다 `MATCH (a {id}), (b {id}) MERGE (a)-[:concernsDam]->(b)` 한 줄을 만든다. 결과는 `kgv4_load.cypher` 파일이고, 이것을 Neo4j에서 실행해 적재한다.
- 실제로 만들어진 Cypher 한 줄과, 그 줄이 무엇을 하는지(MERGE는 없으면 만들고 있으면 갱신)를 예시로 보이면 교수님 질문("JSON에 어떤 형태로 들어가 있냐, Cypher가 뭐냐")에 답이 된다.

**개선할 점**
- 교수님은 "저장은 그렇게 중요하지 않다"고 하셨다. 길게 쓰지 말고 예시 한 줄로 충분하다.

**DDKG로 설명되는가**
- **설명된다.** DDKG 3.3: 추출 결과를 JSON으로 모으고, 온톨로지의 의미·계층 관계에 따라 Python 스크립트가 JSON 키·값을 읽어 Cypher 문을 만들어 일괄 적재한다. Neo4j를 고른 이유는 Cypher로 조회·추가·삭제·수정이 효율적이고 여러 단계를 따라가는 질의에 강하기 때문이다. 4.3.1에서는 댐마다 JSON 파일 하나로 정리해 적재했다.
- 차이는 하나다. 우리는 JSON이 아니라 **CSV(개체·속성·관계 세 표)**로 모은다. 원리(중간 형식으로 모은 뒤 스크립트로 Cypher 생성)는 같다.

### 3.1 검색과 LLM 답변: 전체 흐름

**채워야 할 how**
- 질문 하나가 들어와서 답변이 나갈 때까지 거치는 단계와, 단계마다 무엇이 입력되고 무엇이 나오는지. 교수님이 "질문했을 때 얘가 와서 어느 걸 끌어서 어떻게 가서 뭐가 나오는지 일목요연하게"라고 하신 부분이다.
- 어느 단계를 LLM이 하고 어느 단계를 정해진 코드가 하는지, 코드 파일과 함께. *(코드 확인 필요: `step9_retrieve.py`, `step10_bundle.py`)*

**DDKG로 설명되는가**
- **설명되지 않는다.** DDKG에는 질의응답이나 LLM 답변 생성이 없다. 근거는 Lewis(2020, RAG)와 Zhang(2025) 3.4절이다. GraphAide는 근거로 인용할 수는 있지만 arXiv/학회 논문이라 SCIE 리뷰 대상은 아니다. *(Zhang 원문 확인 필요)*

### 3.2 의도와 근거 구성

**채워야 할 how**
- 의도 규칙(`intents.json`)의 실제 내용: CQ마다 LLM에게 어떤 설명을 주는지, 어떤 근거 구역을 가져오는지.
- LLM에게 주는 프롬프트(`intent_prompt.md`)와 LLM이 내는 출력 형식. *(코드 확인 필요)*

**개선할 점**
- 교수님이 가장 많이 짚은 곳이다. 의도별 경로를 미리 정해 두는 방식이 완전한지, 경로를 어디까지 따라갈지, 미리 정하는 것이 맞는지, 상황에 따라 틀릴 수 있다는 점을 한계로 적고 개선 방향(LLM이나 소형 LLM이 범위를 판단)을 검토하라고 하셨다.
- CQ 재정의 제안(질문↔정보의 관계)도 이 절에 직접 영향을 준다.
- 실행 5번 중 4번에서 CQ2가 빠진 문제(의도 추출이 불안정)가 이미 확인되어 있다.

**DDKG로 설명되는가**
- **설명되지 않는다.** 자료의 근거는 Zhang 3.3("온톨로지의 삼항 23종을 묶어 의도 20개를 얻었다"), 3.4("의도마다 Cypher 질의 규칙을 미리 설계")이다. *(Zhang 원문 확인 필요. 특히 의도 도출 절차와 투표 방식의 상세)*

### 3.3 단계 1. 입력 확인

**채워야 할 how**
- LLM이 낸 의도와 값(댐, 기간)을 어떤 규칙으로 확인하는지: 허용 의도 목록, 허용 댐 목록, 날짜 형식, 맞지 않으면 바꾸는지 거부하는지. 확인 결과 예시. *(코드 확인 필요)*

**DDKG로 설명되는가**
- **설명되지 않는다.** 근거는 Zhang 3.3의 출력 통제(사전 정보, 소수 예시, 정규화 매핑)이다. *(원문 확인 필요)*

### 3.4 단계 2. KG 조회

**채워야 할 how**
- 의도별 Cypher 질의 틀 전체와, 예시 질문에서 실제로 실행된 Cypher, 그 결과로 나온 노드들.
- 경로를 어디까지 따라가는지(몇 단계, 어떤 관계)를 의도마다.

**DDKG로 설명되는가**
- **일부만.** DDKG 4.3.2는 Dam에서 시작해 `(:Dam)-[:exhibitsHazards]->(:HazardForm)` 관계를 따라가고, 계층(`hasSubclass*0..`)으로 범위를 제한하는 Cypher 예시를 보인다. "Dam에서 관계를 따라 개체를 찾는다"는 점은 같다.
- 그러나 DDKG의 조회는 **사람이 조건을 정해 결함 분포를 보는 분석용**이고, 질문에서 의도를 뽑아 질의 틀을 고르는 구조가 아니다. "의도마다 질의 틀을 미리 만든다"는 근거는 Zhang 3.4다.

### 3.5 단계 3. 외부 저장소 조회

**채워야 할 how**
- KG에서 얻은 키(stationCode, variableType, sourceLocator)로 측정자료 저장소와 문서 저장소에서 무엇을 어떻게 꺼내는지. 정각이 아닌 운영 시각이면 앞뒤 정시 두 행을 가져오는 규칙 등. *(코드 확인 필요)*

**DDKG로 설명되는가**
- **설명되지 않는다.** DDKG는 수문 지표를 KG 안(Parameter 노드)에 넣었다. 값은 원래 저장소에 두고 키로 읽는다는 원리는 OntoDSMS(D2RQ의 가상 그래프)에서, 외부 시계열을 불러와 문맥에 더한다는 것은 GraphAide에서 가져왔다.
- 참고로 OntoDSMS의 "복사하지 않고 연결만"은 D2RQ가 SPARQL 질의를 SQL로 번역해 원본 DB를 직접 조회하는 방식이다. 우리는 KG에 키만 두고 코드가 따로 저장소를 읽는 방식이라, 결과(값을 KG에 복사하지 않음)는 같지만 작동 방식은 다르다. 이 차이를 써야 한다.

### 3.6 단계 4. 근거 묶음 구성

**채워야 할 how**
- 묶음을 만드는 세 규칙(의도별 구역, 출처 번호, 원값 그대로)이 코드에서 어떻게 구현되는지, 실제 묶음 한 건. *(코드 확인 필요)*

**DDKG로 설명되는가**
- **설명되지 않는다.** 근거는 Zhang 3.4(KG 지식을 프롬프트에 넣고 우선 사용하게 함)와 RAG다. "출처 번호를 붙인다", "계산한 값을 넣지 않는다"는 문헌에서 직접 온 것이 아니라 우리 설계다. 그렇게 밝혀야 한다.

### 3.7 답변 생성

**채워야 할 how**
- LLM에게 주는 프롬프트 전문(`answer_prompt.md`), 근거 사용 원칙 세 문장, 답변 형식.

**개선할 점**
- 실제 출력에서 이미 발견한 문제(출처 번호 오인용, 근거에 없는 판단, 승인을 수행한 사실로 서술)가 있다. 이것을 걸러내는 장치가 없다는 점이 3.9 한계 3이다.

**DDKG로 설명되는가**
- **설명되지 않는다.** 근거는 Zhang과 RAG다. 근거와 판단을 나눠 쓰게 하는 형식은 우리 설계다.

### 3.8 이전주 대비 수정, 3.9 한계와 향후 계획

**개선할 점**
- 형식 피드백이 이 절에 몰려 있다. 교수님은 이전 대비 변경을 "매번 새로 공부하는 느낌"이라고 하셨다. 다음 자료부터는 확정된 부분을 블록으로 고정하고 바뀐 곳만 표시한다.
- 3.9의 해결방법(에이전트, 의도별 투표, 출처 대조, 실시간 조회, 질문·평가 자료)은 10/19 회의에서 나온 방향(소형 LLM이 경로 범위 판단, CQ 재정의, 검증 데이터셋을 수학 문제 만들듯 구축, 질문 증강)과 합쳐 다시 정리해야 한다.

## 3. 요약: DDKG로 설명되는 것과 안 되는 것

**DDKG로 설명되는 것**
- 온톨로지를 Noy 7단계로 만들고, 모든 최상위 클래스를 Dam에 연결하는 구조 (DDKG 3.1)
- 저장: 중간 형식으로 모은 뒤 스크립트로 Cypher를 만들어 Neo4j에 일괄 적재, Neo4j를 쓰는 이유 (DDKG 3.3, 4.3.1). 우리는 JSON 대신 CSV.

**DDKG로 원리는 설명되지만 우리 자료가 조건과 달라 보충이 필요한 것**
- 별표3 문서에서 별표 블록을 잘라내는 전처리 (DDKG 3.2.1)
- 비고와 별표3에서 규칙으로 값 뽑기 (DDKG 3.2.2): DDKG는 "고도로 정형화된" 경우에만 규칙을 쓴다. 비고가 그 조건을 만족하는지 데이터로 보여야 한다.
- Dam에서 관계를 따라가는 Cypher 조회 (DDKG 4.3.2): 분석용 조회라 질문 응답과는 목적이 다르다.

**DDKG로 설명되지 않아 다른 근거가 필요한 것**
- CQ로 범위를 정하고 Class·관계를 도출하는 방법 → Noy & McGuinness, Li
- 정형 표 전처리(대상 선택, 중복 제거, 표기 통일) → 근거 문헌 없음, 일반적 정제로 정직하게 서술
- 정형 표 매핑 → OntoDSMS(D2RQ)
- 관계 연결(무엇이 일치할 때 잇는지) → Noy, Li
- KG 검증(V1~V5)과 CQ 도달 가능성 확인 → Noy(도메인·범위, 값 제한, CQ 점검), 필요하면 KG 품질 검증 문헌 추가 조사. **자료에서 DDKG 식 (10)~(11)을 근거로 든 것은 바로잡아야 한다.**
- 3장 전체(의도, 입력 확인, 질의 틀, 외부 저장소, 근거 묶음, 답변) → Zhang, RAG(Lewis), OntoDSMS, GraphAide

**문헌 근거 없이 우리가 정한 것 (자체 판단으로 밝혀야 하는 것)**
- 승인과 운영행위를 나눠 비고를 운영행위로 쓴 것
- 관측소코드를 속성이 아니라 관계로 만든 것
- 방류시작시간·접수방류량·비고를 한 속성으로 합친 것 (개선 대상)
- 근거 묶음의 출처 번호 규칙, 계산값을 넣지 않는 규칙, 근거와 판단을 나눠 쓰는 답변 형식

## 4. 이 정리로 정한 진행 순서 제안

1. **DDKG 리뷰** (SCIE, *Advanced Engineering Informatics*)
   - 리뷰하면서 바로 채울 how: 2.3 전처리, 2.5 문서 추출, 2.8 저장, 1장 일부
   - 리뷰하면서 바로잡을 것: 2.7 검증의 근거(DDKG 식 10~11은 분류 라벨 검사)
2. **OntoDSMS 리뷰** (SCIE, *Automation in Construction*)
   - 채울 how: 2.4 구조화 매핑, 3.5 외부 저장소(값을 복사하지 않는 원리)
3. **Zhang 리뷰** (SCIE, *Advanced Engineering Informatics*)
   - 채울 how: 3장 전체(의도, 입력 확인, 질의 틀, 근거 묶음, 답변)
4. **Noy & McGuinness, Li는 리뷰 대상이 아니라 근거 확인용으로 읽기**
   - Noy는 학술지 논문이 아닌 기술 보고서(가이드), Li는 *Water*(MDPI) 게재. SCIE 여부를 따로 확인해야 한다.
   - 채울 how: 1장 CQ, 2.6 관계 연결, 2.7 검증의 근거
