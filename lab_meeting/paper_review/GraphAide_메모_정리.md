- 메모 제목과 같은 색 형광펜으로 원문 문장을 표시함(GraphAide_메모작성본.pdf)

## 1쪽

### 연구 목적

- 여러 출처의 자료로 지식그래프(KG)를 만들고, 그 KG에 자연어로 질의하고 추론하는 시스템 GraphAide를 제안한다
- KG와 LLM을 함께 써서 특정 분야의 디지털 조수를 빠르게 만드는 것이 목표다
- RAG의 설계 방식과 시맨틱 웹 기술(온톨로지)을 합친 에이전트형 LLM 응용이다

### 연구 배경

- LLM은 요약, 연관, 추론에서 성능이 좋아 여러 분야에 빠르게 쓰이고 있다
- KG는 개념을 개체로, 개체 사이를 관계로 나타낸 것이다. 만드는 데는 자료 규모, 분야마다 다른 개념, 구축 비용의 어려움이 있다
- LLM 응용의 큰 문제는 환각(없는 사실을 만들어 냄)이다

### 기본 RAG의 한계와 KG의 역할

- RAG는 질문과 관련된 문맥을 찾아 LLM에 함께 넣어 환각을 줄인다. 기본 RAG는 벡터 DB에서 의미가 비슷한 조각을 찾는다
- 한계: 벡터 검색은 질문과 문서의 의미 유사도에만 의존한다. 문서 사이의 관계, 메타데이터 같은 구조 정보를 쓰지 못한다
- KG는 여러 문서에 흩어진 정보를 관계로 이어 저장하므로 이 한계를 보완한다
→ 의미 문맥(벡터)과 구조 문맥(그래프)을 함께 쓰자는 것이 이 논문의 출발점이다

## 2쪽

### GraphAide의 주요 기능

- 온톨로지에 맞춘 KG 구축: txt, html, pdf 등에서 여러 값, 여러 출처, 시간 속성을 다룬다
- 임베딩 생성과 관리: 벡터 DB를 여러 개 두고 질문에 따라 고른다
- 온톨로지 설정을 틀(template)로 바꿔 끼울 수 있다. 같은 자료로 KG를 여러 판 만들 수 있다
- 문맥 생성 강화: 벡터 검색과 그래프의 부분 그래프 매칭을 합친다
- 외부 함수 실행: 시계열 DB의 시간 자료 같은 다른 형태의 자료를 가져와 문맥에 더한다

### 관련 연구와의 차이

- 기본 RAG: 문서를 조각내 임베딩하고 비슷한 조각을 찾는다. 의미 유사도에만 의존한다
- GraphRAG: KG 위에 색인을 만들고 커뮤니티 탐지로 나눠 전체를 아우르는 답을 만든다
- 그 밖에 특정 분야 글에서 KG를 만드는 연구, 인과 그래프를 뽑는 연구가 있다
- 저자들이 본 공통 한계: 특정 응용에 묶여 있고 확장하기 어렵다

### 구조 개요: 두 단계

- 생성 단계: 여러 출처의 정보를 합쳐 KG를 만든다. KG는 벡터 DB와 함께 지식 저장소가 된다
- 질의 단계: 사용자 질문으로 지식 저장소를 조회하고, 설명과 근거를 붙여 답한다
- 정해진 순서로 실행하는 체인과, LLM의 응답을 보고 다음 질의를 스스로 정하는 에이전트를 섞어 쓴다
- 풀어야 할 문제를 8가지로 나눴다: 자료 적재와 정규화, 개체명 인식, 분야에 맞는 의미 주석, 그래프 모델링과 저장, 질의 해석과 문맥 생성, 질의 확장과 후보 생성, 요약과 설명 가능한 응답 생성

## 3쪽

### A. 자료 적재

- 텍스트, CSV, PDF 등 흔한 형식을 그대로 받는다
- 적재한 자료를 나누고 조각낸다. 벡터 검색을 빠르게 하고, LLM이 한 번에 받을 수 있는 길이를 넘는 자료를 다루기 위해서다
- 조각 크기와 겹치는 길이는 고정값을 쓰고, 분야에 맞게 바꿀 수 있다

### B. 저장

- 기본 RAG와 달리 벡터 DB와 그래프 DB 양쪽에 저장한다
- 벡터 DB: 분야 자료나 범용 지식(WikiData)의 임베딩을 저장한다
- 그래프 DB: 구조 정보를 추가로 저장한다. 저자들은 이것을 이 시스템의 새로운 점이라고 했다

### C. KG 생성

- 하는 일: 개체 추출, 관계 추출, 개체 구분(같은 것인지 가리기), KG 부호화, KG 유지
- 방법: 예시 몇 개를 넣은 프롬프트로 LLM에 KG를 만들게 한다
- 온톨로지(또는 노드·엣지 유형 목록)를 입력으로 준다. 이것이 LLM이 낼 수 있는 응답의 형식을 제한한다
- 만든 부분 그래프가 형식에 맞는지는 Pydantic(형식 검사 도구)으로 확인한다
→ 온톨로지는 KG를 만들 때 LLM의 출력을 묶는 틀로 쓰인다. 온톨로지 자체를 어떻게 만드는지는 이 논문이 다루지 않는다

### D. 부분 그래프 질의 생성

- 사용자 질문은 불완전하고 부정확한 경우가 많아 검색 정확도가 떨어진다
- 질의 확장: 원래 질문의 핵심 개체와 관계는 유지하면서 질문을 여러 판으로 늘린다(틀 기반)
- 늘린 질문들을 LLM이 부분 그래프 매칭 틀로 바꾼다. Neo4j를 지원하고 Cypher 질의를 자동으로 만든다
→ 그래프 질의문을 LLM이 만든다

### E. 지표와 평가

- 구성요소가 여럿인 시스템은 지표 하나로는 성능을 설명하기 어렵다. 구성요소마다 역할과 다루는 자료에 맞는 지표가 필요하다
- 표 I: 개체 추출은 답 정확도, 의미 주석은 문맥 관련성·정확도와 답 관련성·정확도와 의미 유사도, 개체 구분은 문맥 정밀도·재현율과 ROC 곡선, 질의 확장은 답 관련성, 그래프 질의 생성은 답 정확도·관련성
- 평가 자료 준비와 지표 계산에는 RAGAS를 쓴다
- 표 I은 어떤 지표를 쓸지를 정한 것이고, 표의 지표 전부에 대한 결과값은 논문에 없다

### 표 I. 구성요소별 지표

- GraphAide의 구성요소 다섯 개마다 평가에 쓸 지표를 나열한 표다. 지표의 값은 없다

## 4쪽

### 정성 평가

- 사람이 참여해 응답을 평가하는 정성 지표도 필요하다고 했다
- 검색 모델과 LLM을 바꿔 가며 비교할 수 있는 결과를 만들어, 분야 전문가가 평가할 수 있게 한다

### F. 설명 가능한 결과 생성

- 부분 그래프 매칭 결과와 벡터 검색 결과를 합쳐 LLM에 줄 문맥을 만든다
- 늘린 질문마다 LLM에 따로 묻고, 한 번 더 호출해 응답들을 하나로 합친다
- 조건이 여러 개인 복잡한 질의 틀을 자동으로 만드는 것은 향후 과제다

### 실험 구성

- 구성: GPT-4o, Chroma(벡터 DB), Neo4j(그래프 DB), LangChain
- 자료: DARPA AIDA 사업의 뉴스 기사(우크라이나·러시아 분쟁)
- 온톨로지: 기존에 만들어진 것을 가져다 썼다. 개체 유형 약 190개, 사건 유형 약 140개, 관계 유형 약 50개
- 개체 구분의 기준 지식으로 DARPA판 WikiData(DWD)를 썼다

### 그림 1. GraphAide 구조

- KG 생성 단계(왼쪽)와 KG 질의 단계(오른쪽)의 구성요소와 흐름을 나타낸 그림이다

## 5쪽

### KG 생성 결과

- 뉴스 기사 1,846건을 처리해 KG를 만들었다
- 글을 조각내고, 조각마다 부분 KG를 만들어 Neo4j에 넣기를 반복했다
- 글에서 뽑은 개체 언급은 DWD에서 가장 가까운 항목을 찾아 같은 개체로 묶었다

### KG 품질 평가 방법

- 만든 KG를 기존 시스템(GAIA)이 만든 KG와 비교했다
- 비교한 것은 노드 유형과 관계 유형의 분포다(그림 4, 그림 5)
- 기준 KG는 노드 유형이 사람(PER)에 쏠려 있고, GraphAide의 KG는 유형이 더 다양하고 고르게 나왔다고 했다
- 개체 추출과 관계 추출의 품질이 기준 KG보다 좋다고 했으나, 정밀도나 재현율 같은 수치는 없다
→ KG에 들어간 내용이 맞는지를 확인한 것이 아니라, 유형이 얼마나 다양하게 뽑혔는지를 본 것이다

### 노드 유형의 계층 표기

- 노드 유형은 온톨로지의 계층을 따라 가장 구체적인 개념까지 적는다
- 예: GPE_UrbanArea_City는 지정학적 개체 아래 도시 지역 아래 도시를 뜻한다

### 그림 2. DWD 임베딩

- 개체 구분에 쓴 기준 지식(DWD)의 임베딩을 2차원에 찍어, 뜻이 비슷한 항목이 모여 있는 모습을 보인 그림이다

## 6쪽

### 의미 주석(유형 부여) 평가

- 노드에 유형을 붙이는 과정을 RAGAS의 답 관련성, 답 정확도, 의미 유사도로 평가했다
- 답 정확도만으로는 설명되지 않는 경우가 있었다. 예: 정확도는 0.23인데 LLM이 붙인 유형(건물, 철도 기관)이 정답 유형(사무용 건물, 기차역)과 뜻이 가까워 의미 유사도는 0.92였다
- 논문에 나온 수치는 이 예시 하나의 값이고, 전체 평균은 없다

### 질의 단계 평가

- 문맥을 네 수준으로 늘려 가며 같은 질문의 응답을 비교했다(그림 7): LLM만 → 기준 지식(WikiData) 추가 → 분야 문서 추가 → KG 추가
- 문맥을 늘릴수록 응답이 구체적이 된다고 했다
- KG를 쓰면 한 문서에 함께 나오지 않는 개체도 부분 그래프로 이어져 문맥에 들어간다
- 이 비교는 질문 하나에 대한 정성 비교다

### 그림 3. 생성된 KG

- 뉴스 기사에서 생성한 KG의 일부를 그래프 DB 화면으로 보인 그림이다

## 7쪽

### 그림 4, 그림 5. 유형 분포

- 그림 4는 GraphAide가 생성한 KG, 그림 5는 기준 KG의 노드 유형(왼쪽)과 관계 유형(오른쪽) 비율을 나타낸 막대그래프다
- 노드는 기준 KG가 PER에 쏠려 있고, 관계는 GraphAide의 KG가 Contact와 Conflict에 쏠려 있다

### 한계와 향후 과제

- 정량 평가는 하지 않았다. 정밀도, 재현율, 검색 관련성으로 개체 구분, 유형 부여, KG 생성의 개선을 재는 것은 향후 과제다
- 정확도와 관련성의 정량적 개선을 보고하는 정식 평가도 향후 과제다
- 평가 자료와 지표를 자동으로 만드는 API도 향후 과제다(3쪽)

### 정리

- 이 논문이 제시한 것: KG와 벡터 DB를 함께 쓰는 RAG 시스템의 참조 구조와 구성요소
- 온톨로지의 쓰임: 이미 있는 온톨로지를 입력으로 받아, LLM이 KG를 만들 때 낼 수 있는 유형을 제한한다
- 검증: KG는 유형 분포를 기존 KG와 비교했고, 응답은 질문 하나로 정성 비교했다. 정량 결과는 예시 값 하나뿐이다
- 구성요소마다 지표를 따로 둬야 한다는 생각(표 I)은 제시했으나 실제로 측정하지는 않았다

### 우리 연구와의 비교

- 같은 점: 온톨로지를 먼저 두고 그에 맞춰 KG를 만든다. KG는 Neo4j에 저장한다. 질문에 맞는 부분을 KG에서 찾아 LLM의 문맥으로 준다
- 다른 점 1: GraphAide는 그래프 질의문(Cypher)을 LLM이 만든다. 우리는 CQ마다 정해 둔 조회문을 쓰고, LLM은 의도와 값만 뽑는다
- 다른 점 2: GraphAide는 벡터 DB를 함께 쓴다. 우리는 쓰지 않고, 수문 측정값은 따로 둔 저장소에서 댐 코드와 시각으로 조회한다
- 다른 점 3: GraphAide는 기존 온톨로지를 가져다 썼다. 우리는 가져다 쓸 온톨로지가 없어 CQ에서 출발해 직접 설계했다
- 다른 점 4: GraphAide의 KG는 뉴스 글에서 LLM으로 뽑았다. 우리 KG는 승인 기록 같은 정형 자료를 규칙으로 옮긴 부분이 대부분이다

### 그림 6. 의미 주석 평가

### 그림 7. 문맥 수준별 응답 비교

- 같은 질문에 대해 문맥을 네 수준(LLM만, WikiData, 분야 문서, 분야 문서와 KG)으로 달리했을 때의 응답을 나란히 보인 그림이다
